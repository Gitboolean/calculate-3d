# 0002 — Compute cost on the server only; the UI re-requests a quote on every field change

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Anton Pohorielov (автор), architecture-design pass

## Context

Мінімальний донат і розбивку собівартості показують два місця: живий розрахунок (AC-06: перерахунок після кожної зміни поля) і каталог (AC-12…AC-14: ціна за поточними налаштуваннями). Формула має правило округлення з двох частин. Мінімальний донат округлюється вгору з **точної** суми складових, а кожен рядок розбивки — до копійки за звичайними правилами (AC-08). Якщо реалізувати формулу двічі, на різних мовах вона може розійтися на копійку. До того ж у JavaScript немає вбудованого десяткового типу.

## Decision drivers

- QG-1 Точність: 100 % збіг до копійки з еталонною таблицею, 0 випадків «донат < собівартість» (PRD §6).
- QG-2 Чуйність: перерахунок p95 ≤ 300 мс, виміряний як час відповіді сервера на запит розрахунку (PRD §6) — NFR сам передбачає серверний розрахунок.
- §2: гроші — `decimal.Decimal` + `ROUND_CEILING`, `float` заборонено.
- AC-10: зберегти виріб можна лише тоді, коли мінімальний донат показано, і сервер має змогу це перевірити.

## Considered options

1. **Лише на сервері** — одна чиста Python-функція на `Decimal`; UI після паузи в наборі (debounce ≈200 мс) запитує перерахунок, відповідь кешується за ключем із вхідних значень.
2. **Дубль: TypeScript (decimal.js) для миттєвого показу + Python для каталогу** — нульова затримка, але дві реалізації й подвійна еталонна таблиця.

**Розглянуто й виключено обмеженням** (не рівноцінна альтернатива):

- *Лише на клієнті* — PRD §6 міряє latency як «час відповіді сервера на запит розрахунку», а AC-10 вимагає, щоб сервер міг перевірити збереження виробу.

## Decision outcome

**Chosen:** Option 1. Формула живе в одному місці — чистому доменному коді бекенду (без I/O, unit-тести проти еталонної таблиці; модуль-власник визначає SAD §5). Її використовують і ендпоінт розрахунку, і каталог (ADR 0003). UI нічого не рахує: він показує те, що повернув сервер для **поточних** вхідних даних. Ключ запиту TanStack Query — це нормалізовані введені значення, тож при їх зміні стара ціна не показується як актуальна (AC-06).

## Consequences

**Positive**
- Розрахунок і каталог не можуть розійтися: обидва викликають ту саму функцію.
- Еталонна таблиця одна (pytest), веб не має математики грошей — лише форматування `Intl.NumberFormat('uk-UA')`.
- AC-10 перевіряється на сервері: збереження виробу проходить через ту саму валідацію, що й розрахунок.

**Negative**
- Ціна з'являється через debounce + час відповіді, а не миттєво; на `127.0.0.1` це десятки мілісекунд, але UI потребує стану «перераховується…».
- Кожна зміна поля — HTTP-запит; потрібен debounce і скасування застарілих запитів, щоб не заливати сервер під час набору.

**Neutral**
- Запит розрахунку нічого не пише в БД (розрахунок існує лише на екрані — CONTEXT «розрахунок»), тож його можна безпечно повторювати.
