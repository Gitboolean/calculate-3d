# 0006 — Enforce name uniqueness via a casefolded name_key column; search and sort names in Python

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Anton Pohorielov (автор), architecture-design pass

## Context

Назви пластиків і виробів мають бути унікальними без урахування регістру, причому після обрізання пробілів на початку й у кінці (AC-02, AC-11: «PETG чорний » — повтор «PETG чорний», «брелок-тризуб» — повтор «Брелок-тризуб»). Каталог шукає за частиною назви без урахування регістру й сортує так: спершу латиниця, потім кирилиця за українською абеткою (… г ґ д е є … и і ї й …) — AC-12. Назви переважно кириличні. У SQLite `COLLATE NOCASE`, `lower()`/`upper()` і `LIKE` зводять регістр **лише для ASCII**, тож для SQLite «Тризуб» і «тризуб» — різні рядки, а її порядок не збігається з українською абеткою (ґ, є, і, ї стоять поза діапазоном а–я).

## Decision drivers

- AC-02, AC-11 — унікальність без урахування регістру після trim; AC-12 — пошук і український абетковий порядок.
- §2: «БД як тупе сховище» — без CHECK/TRIGGER, проте індекси (зокрема UNIQUE) дозволені; валідація — у Pydantic/сервісі.
- ADR 0003: каталог і так завантажує всі вироби в пам'ять для перерахунку цін.
- ADR 0005: правило спільне для двох модулів (`pricing`, `catalog`).

## Considered options

1. **Колонка `name_key` + UNIQUE-індекс; пошук і сортування в Python** — `name_key = casefold(trim(name))` обчислює застосунок; UNIQUE на `name_key` гарантує інваріант на рівні БД; пошук і порядок рахує спільна утиліта `core/text.py`.
2. **Лише перевірка в сервісі** — без додаткової колонки й індексу; сервіс порівнює casefold-назви перед записом. Для одного користувача гонок немає, але інваріант тримається тільки на коді.
3. **Власна collation у SQLite** (`create_collation('uk_ci')` на кожному з'єднанні) — БД сама сортує й перевіряє унікальність, але файл БД стає залежним від застосунку (консоль `sqlite3` і сторонні інструменти падають з «no such collation»), а `LIKE` лишається ASCII-only.

## Decision outcome

**Chosen:** Option 1.

- `core/text.py` (спільне для модулів, без бізнес-правил конкретного модуля): `normalize_name(raw) -> str` (trim), `name_key(name) -> str` (`casefold()` нормалізованої назви), `contains(name, query) -> bool` (підрядок у casefold) і `sort_key(name)` — кортеж «група письма (латиниця = 0, кирилиця = 1, інше = 2) + позиції літер у явно заданій українській абетці», без залежності від локалі ОС.
- Таблиці пластиків і виробів зберігають `name` (як ввів автор, без пробілів на краях) і `name_key` з UNIQUE-індексом. Сервіс перевіряє зайнятість заздалегідь і повертає `AppError` з `field`, щоб UI показав помилку біля поля. Порушення UNIQUE в БД (яке могло б виникнути лише через баг) теж перетворюється на ту саму доменну помилку.
- Каталог фільтрує й сортує в пам'яті в тому самому проході, що й перерахунок цін (ADR 0003); SQL `LIKE`/`ORDER BY name` для назв не використовуються.

## Consequences

**Positive**
- Унікальність гарантує БД, навіть якщо в сервісі колись з'явиться баг.
- Правила регістру й абетки — одна чиста функція з unit-тестами на приклад з AC-12 («Benchy, гачок, ґудзик, єдиноріг, Іграшка, Ялинка»).
- Не залежить від ICU, локалі ОС чи версії SQLite.

**Negative**
- Зайва колонка, яку треба оновлювати разом із `name` при кожному перейменуванні (AC-14b); repo пише обидві з одного значення.
- Сортування й пошук неможливо перенести в SQL без повторного рішення (доречно лише разом із пагінацією, див. §7).

**Neutral**
- Якщо колись знадобиться ширше порівняння (наприклад «е» = «є»), змінюється лише `name_key()` + разова міграція перерахунку ключів.
