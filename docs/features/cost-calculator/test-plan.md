# Test plan — cost-calculator

Інструмент рахує мінімальний донат виробу (собівартість, округлена вгору до копійки) з налаштувань
цін і параметрів друку, зберігає вироби в каталог лише як параметри, а ціну перераховує щоразу, коли
її показує. Доступ має лише автор на своєму комп'ютері. Нижче кожен AC з `PRD.md §5` прив'язано
щонайменше до одного тесту.

Поверхні (`sad.md` `target_surfaces`): `backend-service`, `web-frontend`.

## Edge cases / error paths

- Кожен error/authorization AC (AC-02, AC-03, AC-05, AC-07, AC-09, AC-11, AC-14c, AC-16, AC-16b) має
  окремі рядки вище, не злиті з happy path.
- Неіснуючий пластик у розрахунку чи виробі (видалено в іншій вкладці) → донату немає, причина
  «пластик не знайдено» біля рядка; виріб не збережено.
- Видалення неіснуючого пластику чи виробу → «не знайдено», нічого не змінено.
- Перший запуск, налаштування ще не збережено → читання налаштувань повертає «не задано», а не
  нулі; розрахунок поводиться за AC-09.
- Кілька помилок одночасно (AC-05, AC-07) → відповідь перелічує **всі** хибні поля, а не лише перше.
- Назва з текстом, схожим на розмітку чи скрипт (`<script>…`, `<b>`) → зберігається і показується як
  звичайний текст, нічого не виконується (PRD §6.1, component).
- Назва з різним регістром кирилиці й літерами «ґ/є/і/ї» → унікальність і пошук без урахування
  регістру працюють і для них (unit, `name_key`).
- Брак 100 % → донат удвічі більший за собівартість без браку, а не помилка (межа включна, unit).
- Неточне ділення зносу (наприклад 30 000 ÷ 7 000) → показ знос/год до копійки, розрахунок із
  точного значення (unit).
- Дуже великі значення (100 000 г, 500 год) → без переповнення, результат у копійках цілий (unit).
- Відповідь на попередній запит розрахунку приходить пізніше за новий → на екрані лишається ціна
  для останніх значень (component).
- БД недоступна чи не вдався commit → відповідь про внутрішню помилку у форматі problem+json, дані
  не змінено частково (integration — уже покрито тестами `core/errors` і `get_connection`).

## Test data

- **Seed strategy:** фабрики в `backend/tests/factories.py` (з `data-model.md` § Test fixtures), які
  пишуть через SQLAlchemy Core у `Connection`: `make_plastic`, `make_price_settings` (дефолти AC-04),
  `make_item` (виріб разом із рядками витрати), `seed_catalog_volume(items=1000, plastics=50, seed=…)`
  для тестів латентності. Назви товарні («PETG чорний», «Брелок-тризуб», `Item-<n>`) — без PII.
  Вебові component-тести беруть фіксовані відповіді, типізовані згенерованою схемою API.
- **Integration dependency:** справжній тимчасовий файл SQLite, мігрований до `head` тим самим
  ланцюжком Alembic, що й у production. Контейнер не потрібен: SQLite вбудована, а сам файл і є
  ефемерною справжньою залежністю. Сховище даних не мокаємо.
- **Cleanup boundary: per-test.** Зараз `engine` у `conftest.py` має scope на всю сесію, тож тести,
  що пишуть у БД, ділили б стан (унікальні назви, singleton налаштувань). Тому тест, що пише в БД,
  отримує свій чистий файл: один раз на сесію мігрований шаблон копіюється в тимчасову теку тесту
  (без повторних міграцій). Тести «збереженість після перезапуску», E2E і латентність завжди
  працюють на власному файлі. Unit-тести стану не мають.

## NFR validation (load)

- **Latency p95 перерахунку ≤ 300 мс** → після прогріву ≥ 50 послідовних запитів розрахунку (один
  користувач — паралельності немає) зі змінними параметрами; p95 часу відповіді сервера ≤ 300 мс.
- **Latency p95 відкриття каталогу ≤ 500 мс** → дані `seed_catalog_volume(1000 виробів, 50
  пластиків)`, після прогріву ≥ 50 запитів каталогу з перерахунком цін усіх виробів; p95 ≤ 500 мс.
  Додатково перевіряємо, що кількість запитів до БД на одне відкриття каталогу не залежить від
  кількості виробів (без N+1).
- Обидва тести міряють на локальній машині автора і **пропускаються, коли задано `CI`** (SAD §10
  QG-2): спільні ранери дають хибно-червоні прогони.
- **Точність розрахунку (100 % збіг до копійки)** → еталонна таблиця ≥ 10 рядків (unit,
  параметризовано): AC-06, AC-06b, AC-08b, AC-13, плюс тариф 0 ₴, брак 0 %, брак 100 %, неточне
  ділення зносу, частки грама (0,01 г), кілька пластиків із різними цінами, лише хвилини без годин.
  Очікувані значення рахуємо вручну один раз і фіксуємо в таблиці. Плюс перевірка на детерміновано
  згенерованих даних, що донат ≥ собівартості (рядок AC-08).
- **Збереженість (100 % змін після перезапуску)** → integration: зберегти налаштування, пластик і
  виріб через перший екземпляр застосунку → закрити всі з'єднання → новий екземпляр на тому самому
  файлі → прочитати й порівняти всі поля.
- **Локалізація** → unit: 11525 коп → «115,25 ₴» (з нерозривним пробілом від форматера); component:
  тексти сторінок українською; ручний перегляд перед релізом.
- Throughput / Availability — N/A у PRD §6 (один користувач, локальний інструмент).
