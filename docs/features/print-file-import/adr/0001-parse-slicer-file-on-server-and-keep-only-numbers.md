# 0001 — Parse the slicer file on the server and keep only the numbers

- **Status:** Accepted
- **Date:** 2026-11-09
- **Deciders:** Anton Pohorielov (автор), architecture-design pass

## Context

Імпорт (PRD US-01, US-02) починається з файлу слайсера — ZIP-архіву Bambu Studio (`.gcode.3mf`). Службові частини в ньому: `3D/3dmodel.model` (XML, позначка `Application`), `Metadata/model_settings.config` (XML, пластини та їхні `gcode_file`), `Metadata/slice_info.config` (XML, результати нарізки: `prediction`, `weight`, `<filament id type color used_g>`), `Metadata/project_settings.config` (JSON, назви пресетів `filament_settings_id`). Кожен файл треба перевірити ланцюжком AC-12 (проєкт слайсера → нарізаний → рівно одна нарізана пластина → цілісність → межі), витягти філаменти й час і застосувати правила AC-03/AC-09. Питання — де це робиться: у бекенді чи в браузері. Перенесення парсера між мовами пізніше означає переписати його й увесь набір тестів (≥ 3 днів).

## Decision drivers

- QG-1 Точність імпорту — 100 % збіг на еталонних файлах, 0 тихих хибних імпортів (PRD §6, §7).
- QG-2 Стійкість до поганих файлів — 100 % пошкоджених, підроблених і «бомбових» файлів відхиляються без збою (PRD §6); security review фокусується на безпечному читанні архіву (PRD §6.1).
- PRD §6 вимірює затримку як «час відповіді сервера на еталонних файлах і згенерованому файлі 100 МБ».
- cost-calculator ADR 0002: доменні обчислення живуть лише на сервері, UI лише показує результат.
- SAD §2: розбір лише stdlib-засобами (`zipfile`, `xml.etree.ElementTree`, `json`), без нових залежностей.

## Considered options

1. **Розбір на сервері** — браузер надсилає файл, модуль імпорту розбирає його в пам'яті й повертає філаменти, час і підказані зіставлення; файл відкидається.
2. **Розбір у браузері** — SPA відкриває ZIP JS-бібліотекою (fflate / JSZip) і надсилає на сервер лише витягнуті числа в JSON.
3. **Гібрид** — браузер дістає з ZIP чотири службові частини (≈ 70 КБ) і надсилає їх у JSON, а сервер застосовує правила.

## Decision outcome

**Chosen:** Option 1. Лише цей варіант тримає всі правила імпорту (ланцюжок перевірок, округлення часу, нормалізацію кольору й назви, межі файлу) в одному місці з розрахунком, а в pytest їх перевіряють на справжніх еталонних і поганих файлах. Варіанти 2 і 3 переносять частину домену та відповідальність за безпеку архіву в TypeScript і не дають серверу побачити архів цілком, тому перевірка цілісності (AC-13) стає неповною.

Розбір — чиста функція модуля імпорту над `bytes`, без I/O. Вона повертає:

- пластину, яку імпортовано (номер і назва — Decision override §1);
- `print_time_s`: `prediction` (повний розрахунковий час разом зі змінами філаменту), округлений вгору до цілої хвилини (AC-03);
- філаменти з ненульовою витратою: назва пресету (без пробілів на краях), тип, колір `#RRGGBB` (верхній регістр, без альфи — AC-09), `usage_mg` (ADR 0004);
- для кожного філамента — `plastic_id` запам'ятованого зіставлення, якщо воно є.

Під час розбору в БД нічого не пишеться; файл не потрапляє на диск і не логується.

## Consequences

**Positive**
- Одне джерело правди для правил імпорту; тест-таблиця еталонів (`vtulka_A`, `LITTLE_TREES`) та набір поганих файлів запускаються в `make api-check`.
- Розбір має доступ до всього архіву (каталог ZIP, розміри частин), тож цілісність і «бомби» перевіряються до розпакування (SAD §8).
- Вебу не потрібна бібліотека ZIP; новий формат слайсера (OrcaSlicer) додається лише в бекенді.

**Negative**
- Файл до 100 МБ передається в бекенд і на час запиту тримається в пам'яті; для цього треба змінити `RequestGuard` (ADR 0002).
- Сервер розбирає недовірені дані — помилка парсера стає помилкою сервера, тож потрібні жорсткі межі читання (SAD §8) і тест «0 збоїв» на поганих файлах.

**Neutral**
- Якщо колись знадобиться розбирати в браузері (наприклад, офлайн-режим), чиста функція розбору лишається еталоном для порівняння.
