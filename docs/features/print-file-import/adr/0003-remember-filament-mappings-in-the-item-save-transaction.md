# 0003 — Remember filament mappings in the item-save transaction

- **Status:** Accepted
- **Date:** 2026-11-09
- **Deciders:** Anton Pohorielov (автор), architecture-design pass

## Context

Зіставлення пластиків — запам'ятаний вибір «філамент слайсера (назва + колір) → пластик» (CONTEXT). AC-07 вимагає, щоб вибір запам'ятовувався, **коли автор зберігає виріб** (новий із розрахунку чи підтверджене «було → стало»), і не запам'ятовувався, якщо виріб не збережено. AC-08 додає: новий вибір замінює зіставлення, а вибір для філамента, чий рядок автор потім видалив, усе одно запам'ятовується. AC-11: видалення пластику зіставленням не блокується, а зіставлення забувається. Питання — як прив'язати запис зіставлень до збереження виробу, яке належить модулю `catalog`.

## Decision drivers

- PRD AC-07, AC-08, AC-11; NFR «Збереженість зіставлень» (100 % після перезапуску).
- Конвенція «одна транзакція на запит» (`core/db.py::get_connection`, `BEGIN IMMEDIATE`).
- project ADR 0002: модулі спілкуються лише через `service.py` іншого модуля.
- Інваріант CONTEXT: видалений пластик ніколи не підставляється.

## Considered options

1. **У транзакції збереження виробу** — `ItemInput` (створення й оновлення виробу в `catalog`) отримує необов'язковий список зіставлень; `catalog.service` у тій самій транзакції викликає сервіс модуля імпорту.
2. **Окремий запит після збереження** — веб спершу зберігає виріб, а після успіху окремим `PUT` до модуля імпорту записує зіставлення.
3. **Окремий ендпоінт «зберегти з імпорту»** — модуль імпорту сам викликає `catalog.service.create_item/update_item` і записує зіставлення в одній транзакції.

## Decision outcome

**Chosen:** Option 1.

- `ItemInput` отримує необов'язкове поле зі списком зіставлень `{filament_name, filament_color, plastic_id}` (назви полів і межу довжини фіксують api-forge і data-model). Ручне збереження без імпорту його не передає, і поведінка етапу 1 не змінюється.
- `catalog.service.create_item` / `update_item` після запису виробу викликає `importing.service.remember_mappings(conn, mappings)` з тим самим `Connection`. Якщо виріб не зберігся (`409` на назву, `404`, межі `costing`), транзакція відкочується, і зіставлень не лишається. Якщо не записалися зіставлення (пластик, на який вказує зіставлення, тим часом видалено → FK), відкочується і виріб.
- Запис — upsert за ключем `(filament_name, filament_color)`: новий вибір замінює старий (AC-08). Пластик зіставлення не мусить бути серед рядків виробу (AC-08: видалений рядок).
- Колонка `plastic_id` таблиці зіставлень — FK на `plastics(id)` з `ON DELETE CASCADE`: видалення пластику забуває його зіставлення на рівні БД (AC-11), тож `pricing` про зіставлення не знає, а `ItemInUse` і далі блокують лише вироби.
- Залежності сервісів: `catalog.service → importing.service → pricing.service`; циклу на рівні `service.py` немає (`tests/unit/test_module_boundaries.py`).

## Consequences

**Positive**
- AC-07 виконується дослівно: «збережено виріб» ⇔ «запам'ятовано зіставлення», без проміжного стану.
- Один шлях збереження виробу у вебі (`features/save-item`); імпорт лише додає поле.
- AC-11 закривається каскадом FK без коду в `pricing`.

**Negative**
- `catalog` залежить від модуля імпорту, а його API знає поняття «філамент слайсера» — модуль каталогу стає ширшим.
- Каскадне видалення — поведінка FK, яку треба покрити тестом (видалити пластик → наступний імпорт знову питає), бо в коді її не видно.

**Neutral**
- Варіант 2 (дві транзакції) дав би лише видиму незручність (імпорт знову питає пластик), але не виконує AC-07 дослівно. Варіант 3 дублює шлях збереження виробу з тими самими помилками й правилами.
