# Test plan — print-file-import

Автор завантажує нарізаний файл проєкту Bambu Studio у розрахунок або в наявний виріб. Інструмент
бере з файлу повну витрату кожного філаменту й час друку, округлює їх лише вгору, підставляє
запам'ятані зіставлення пластиків (або просить обрати пластик, і вибір запам'ятовується разом зі
збереженням виробу), показує «було → стало» і рахує мінімальний донат тією самою формулою, що й для
ручного введення. Непридатний файл відхиляється з поясненням і нічого не змінює, а сам файл ніколи не
зберігається. Нижче кожен AC з `PRD.md §5` прив'язано щонайменше до одного тесту.

Поверхні (`sad.md` `target_surfaces`): `backend-service`, `web-frontend`.
Входи: [PRD](PRD.md) §5–§6.1 · [SAD](sad.md) §6 (потоки 1–7, cross-cutting), §8, §10 (QG-1…QG-4) ·
[data-model](data-model.md) · [contracts/openapi.yaml](contracts/openapi.yaml) ·
[tasks.json](tasks/tasks.json) (T1–T17 — назви тестових файлів у `files_hint` узгоджено з цим планом).

| AC-15 | інструмент недоступний з іншого пристрою | unit | сервер слухає лише `127.0.0.1` (наявний тест bind-адреси) |
| AC-15 | запити самого інструмента проходять | integration | імпорт від локального UI (дозволений хост, той самий origin, сирий файл) успішний |

## Edge cases / error paths

- Кожен error/authorization AC (AC-04, AC-06, AC-09b, AC-12, AC-13, AC-14, AC-15) має окремі рядки
  вище, не злиті з happy path. Кожна причина відмови з набору поганих файлів — окремий
  параметризований випадок, щоб регресія одразу називала зламану перевірку.
- **Набір поганих файлів** (SAD §10 QG-2; генератор `tests/fixtures/slicer/bad_files.py`, integration,
  кожен випадок < 5 с, жодної внутрішньої помилки сервера, БД без змін):
  - не ZIP; обрізаний ZIP; порожнє тіло → «файл пошкоджений» / «не файл проєкту»;
  - каталог архіву з 10 001 записом → «файл пошкоджений»;
  - службова частина понад 8 000 000 байт розпакованого розміру → «файл пошкоджений»;
  - заголовок, що бреше про розмір частини (розпаковується більше, ніж заявлено) → читання
    зупиняється на межі, «файл пошкоджений»;
  - ZIP-бомба в G-code (розпаковується в гігабайти, стиснута < 1 МБ) → G-code не розпаковується
    взагалі (SAD §8 «Межі читання архіву»): відповідь < 5 с без зростання пам'яті, а результат
    визначають лише 4 службові частини. Очікувану причину відмови фіксує генератор (T2);
  - понад 32 різні пари (назва, колір) або витрата понад межу точного цілого → «файл пошкоджений» /
    порушена межа, без переповнення;
  - XML із «billion laughs» або зовнішньою сутністю (XXE) → відмова без розгортання сутностей і без
    читання зовнішніх ресурсів (unit закріплює поведінку XML-парсера, SAD §2);
  - дубльовані назви службових частин; підроблені внутрішні шляхи (`../`) → «файл пошкоджений»,
    нічого не записано на диск.
- **Пластик видалено між розбором і збереженням виробу** (інша вкладка) → збереження відхиляється з
  поясненням «пластик не знайдено», транзакція відкочується повністю: ні виробу, ні рядків, ні
  зіставлень (integration; SAD §6 потік 6).
- **Зіставлення вказує на пластик, якого вже немає** — неможливо через каскад; integration-тест
  перевіряє, що міграція справді створює `ON DELETE CASCADE` і що `foreign_keys=ON` діє.
- **Назва філаменту, схожа на розмітку чи скрипт** (`<img onerror=…>` у назві пресету) → показується
  як звичайний текст, нічого не виконується (component; PRD §6.1).
- **Назва філаменту довша за 200 символів** у файлі → «файл пошкоджений» (unit); у запиті збереження
  виробу → відмова валідації (integration).
- **Колір у неочікуваній формі** (`#FFF`, `white`, порожньо) → «файл пошкоджений» (unit); у запиті
  збереження → відмова валідації за шаблоном `#RRGGBB` (integration).
- **Подвійне натискання «Імпортувати»** / нова відповідь розбору приходить пізніше за новіший файл →
  у формі лишається результат останнього обраного файлу (component).
- **Імпорт у виріб, який видалили в іншій вкладці** → підтвердження «було → стало» отримує «виріб
  не знайдено», нічого не створено (integration).
- **Відмова захисту запитів** настає до читання тіла: 100 МБ від чужого сайту не читаються в пам'ять
  (integration).

## NFR validation (load)

- **Latency p95 імпорту ≤ 5 с для будь-якого файлу до межі розміру** → для кожного з трьох еталонів і
  згенерованого валідного файлу рівно 100 000 000 байт: прогрів, потім 20 послідовних запитів розбору
  (один користувач — паралельності немає); p95 часу відповіді сервера ≤ 5 с. Відмальовування в
  браузері не входить (PRD §6). SAD §10 QG-4.
- **Межа розміру ≤ 100 МБ** → файл 100 000 001 байт відхиляється як завеликий, а сервер не читає
  тіло далі за межу (рядок AC-13). Цей тест швидкий і працює скрізь.
- Тест латентності входить у `make check` і працює так само, як NFR-тести латентності етапу 1:
  міряє на локальній машині автора й **пропускається, коли задано `CI`** (спільні ранери дають
  хибно-червоні прогони; SAD §10 QG-4 «на тій самій машині, що й NFR-тести етапу 1»).
- **Точність імпорту (100 % збіг зі слайсером)** → параметризована таблиця «еталон → очікуваний
  результат розбору й мінімальний донат» (integration, SAD §10 QG-1): `vtulka_A` 11,54 г / 1 год 38 хв /
  18,82 ₴ і 22,00 ₴ після зміни ціни; LITTLE_TREES 15,49 / 2,23 / 2,36 г, 1 год 31 хв, пластина 1;
  перенарізка AC-05 80,63 → 60,73 ₴. Плюс unit-приклади AC-03. KPI «0 г / 0 хв на 5 реальних
  імпортах» — ручна звірка з екраном слайсера (PRD §7), не автотест.
- **Стійкість до поганих файлів (100 % відхилено)** → набір поганих файлів у «Edge cases» (integration).
- **Файл не зберігається (0 байтів на диску)** → integration: знімок тимчасового каталогу ОС і
  каталогу БД до та після успішного й відхиленого імпорту; різниці немає (крім файлів самої БД / WAL).
- **Збереженість зіставлень (100 % після перезапуску)** → integration: зберегти виріб зі
  зіставленнями через перший екземпляр застосунку → закрити всі з'єднання → новий екземпляр на тому
  самому файлі БД → розбір підставляє той самий пластик.
- **Локалізація (100 % повідомлень українською)** → unit: кожне повідомлення доменних помилок модуля
  `importing` українською; component: тексти слайсу українською, назви філаментів показано як є;
  ручний перегляд перед релізом.
- Throughput / Availability — N/A у PRD §6 (один користувач, локальний інструмент).
