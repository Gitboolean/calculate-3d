# Idea Brief — calculate-3d

## 1. Raw idea
«продукт для власного користування який буде мені допомагати рахувати собівартість 3d друку щоб я розумів яку ціну ставити для продажу за донат на ЗСУ»

## 2. Problem
Ціну на надруковані вироби, які продаються за донат на ЗСУ, зараз ставлять «на око», і собівартість не рахують узагалі. Через це невідомо, чи кожен продаж хоча б покриває пластик, електрику, знос принтера і брак. Частина виробів може непомітно продаватися в мінус, і тоді автор доплачує зі своїх коштів.

## 3. Users
- **Один користувач — автор.** Мейкер з одним 3D-принтером, продає вироби за донат на ЗСУ.
- Друкує як нові разові моделі, так і ті самі вироби багато разів.
- Ціну рахує на комп'ютері поруч зі слайсером (Bambu Studio / OrcaSlicer), одразу після нарізки моделі.
- Частота: ≈3 розрахунки на тиждень (≈40 за квартал), з них нові вироби й повторні продажі.

## 4. Why now
Продажі за донат уже йдуть, а ціни ставляться без розрахунку, тож кожен наступний продаж — це ризик збитку. Крім того, це навчальний проєкт: на ньому автор хоче пройти повний SDLC-пайплайн. Бюджет — 2–4 тижні без поспіху.

## 5. Out of scope
- Оплата праці автора, пакування, доставка (свідомо не входять у собівартість).
- Націнка чи маржа: собівартість — це **мінімальний донат**, а все понад неї покупець донатить на власний розсуд.
- Облік продажів і аналітика зібраних донатів.
- Кілька принтерів, кілька користувачів, доступ з телефона.
- Окремий розрахунок для кожного кольору в багатоколірному друці (див. §15).
- Публічна картка ціни для покупця.

## 7. Strategic approaches

### Approach A — Ручний калькулятор із каталогом
- **Thesis:** одна форма: вводиш вагу й час зі слайсера, і за збереженими налаштуваннями (ціна філаменту, тариф, знос за годину, % браку) одразу бачиш мінімальний донат у грн; розрахунок можна зберегти в список виробів.
- **For whom:** автор біля слайсера, один принтер.
- **Outcome metric:** час розрахунку нового виробу: «на око» → < 1 хв; збережений виріб — миттєво.
- **Key trade-off:** вагу й час доводиться переписувати вручну, можливі помилки.
- **Effort signal:** S
- **Recommended?** ◯ (стає етапом 1 у C)

### Approach B — Файл зі слайсера → картка донату
- **Thesis:** перетягуєш файл проєкту — інструмент сам зчитує вагу, час і пластик та готує прозору картку для покупця «собівартість X ₴, усе понад — на ЗСУ».
- **For whom:** мейкер, який хоче рахувати без ручного введення і викликати довіру прозорою ціною.
- **Outcome metric:** ≤ 15 с від експорту зі слайсера до готової картки.
- **Key trade-off:** залежність від формату файлу слайсера; без каталогу; обсяг на верхній межі бюджету.
- **Effort signal:** M
- **Recommended?** ◯

### Approach C — Імпорт зі слайсера + каталог
- **Thesis:** перетягуєш файл зі слайсера — інструмент сам бере вагу, час і тип пластику, додає електрику, знос і % браку та показує мінімальний донат у грн; виріб зберігається в каталог, тож для повторних друків ціна видна одразу.
- **For whom:** автор, який друкує і нові, і повторювані вироби.
- **Outcome metric:** новий виріб ≤ 60 с, збережений ≤ 5 с (зараз — «на око»).
- **Key trade-off:** без аналітики донатів, без розбивки за кольорами, брак — середній %, а не фактичний облік.
- **Effort signal:** M
- **Recommended?** ●

## 8. Multi-perspective feedback

### Engineer
- A — найменша поверхня інтеграції, зовнішніх залежностей немає, ламатися майже нічому.
- B і C спираються на недокументований формат файлу слайсера: після оновлення імпорт може тихо зламатися.
- B додає окремий шар генерації картки, але не має каталогу.
- C потребує ручного введення як запасного шляху на випадок збою імпорту.

### Executive
- A вирішує проблему «на око» вже за ~1 тиждень.
- B найкраще продає ідею донату, але без каталогу не виконує критерій для повторних виробів.
- C виконує обидва критерії швидкості й вкладається в бюджет; найкраще співвідношення цінності й зусиль для навчального проєкту.
- Ціна втраченої можливості: A не дає досвіду інтеграції, B витрачає час на картку замість каталогу.

### UX-researcher
- A: щоразу переписувати вагу й час — невелике тертя, але ризик помилок.
- B: найменше тертя для нового виробу, але повторні друки знову вимагають імпорту.
- C: тертя як у B для нового виробу і миттєвий результат для повторних — найкраще вписується в процес «нарізав → порахував».
- B і C без запасного ручного введення лишають користувача ні з чим, якщо імпорт зламався.

### Synthesis matrix
|         | Engineer | Executive | UX |
|---------|:--------:|:---------:|:--:|
| App. A  | + мінімум залежностей, без крихкості | + швидко, проблему закрито | 0 ручне введення, ризик помилок |
| App. B  | − крихкий імпорт плюс картка | 0 картка гарна, каталогу немає | 0 швидкий імпорт, повтори повільні |
| App. C  | 0 крихкий імпорт, решта проста | + обидва критерії, у бюджеті | + найменше тертя загалом |

## 9. Trade-offs and edge cases

### Trade-offs per approach
| Approach | Pros | Cons |
|---|---|---|
| A | Найдешевший (S), найнадійніший, працює за тиждень | Ручне перенесення даних, помилки введення, мало навчання інтеграції |
| B | Найшвидший новий розрахунок, сильна «донатна» історія | Крихкий імпорт, немає каталогу, картка може прив'язати донати до мінімуму |
| C | Обидва критерії швидкості, закриває ринкову прогалину | Залежність від формату файлу, обсяг на межі бюджету (E = 4) |

### Edge cases
- **Багатопластинний проєкт:** у файлі кілька пластин, а взято лише одну.
- **Ненарізаний проєкт:** у файлі немає ваги й часу — потрібне зрозуміле повідомлення і перехід до ручного введення.
- **Відходи на промивку при зміні кольору:** вони можуть дорівнювати вазі моделі або перевищувати її, тож важливо брати повну витрату пластику, а не вагу моделі.
- **Невідомий тип пластику:** тип із файлу відсутній у списку цін — не можна мовчки підставляти 0.
- **Різні ціни пластиків:** PLA, PETG, TPU, композити коштують від 400 до 1500+ ₴/кг, тому потрібна ціна для кожного пластику, а не одна на все.
- **Одиниці введення:** «1h30» проти 1.5 проти 90 хв; грами проти кілограмів.
- **Довгі друки й брак:** зрив 20-годинного друку на 18-й годині — це повний передрук, а не +10%.
- **Друк під час відключень:** енергія від генератора чи зарядної станції коштує в 3–5 разів дорожче.

## 10. Risks
- **TOP — застарілі ціни в каталозі.** Якщо зберігати готову ціну, а не перераховувати її з поточних налаштувань, то після подорожчання пластику чи тарифу повторні вироби тихо продаються в мінус, і саме «миттєва ціна» заважає це помітити. Пом'якшення: каталог зберігає вагу й час, а ціна завжди рахується з поточних налаштувань.
- **Тихий хибний імпорт:** правдоподібна, але занижена ціна без помилки (див. §9).
- **Зміна формату слайсера:** імпорт ламається після оновлення; пом'якшення — ручне введення як запасний шлях.
- **Обсяг перевищує бюджет:** перша робоча версія не з'являється; пом'якшення — етап 1 (ручне введення + каталог) дає робочий інструмент за ~1 тиждень.
- **Фіксований % браку** систематично занижує вартість великих виробів.

## 11. RICE — Claude proposed
- **Reach (R)**: 40 розрахунків/квартал — ≈3 на тиждень, кожен зараз «на око» (§3). Метрику адаптовано: користувач один, тому рахуємо розрахунки, а не людей.
- **Impact (I)**: 2 — собівартість зараз не рахується взагалі (§2); оцінка користі в §8 ставить C «+».
- **Confidence (C)**: 0.8 — ключові факти конкретні; два відкриті питання в §15 (стабільність формату файлу, багатоколірний друк).
- **Effort (E)**: 4 людино-тижні — Effort signal M у §7, скоригований угору користувачем (верхня межа бюджету).
- **RICE = 40 × 2 × 0.8 / 4 = 16** (для порівняння: A ≈ 64 при E = 1; B ≈ 16 при E = 4)
- **State**: confirmed

## 12. Feasibility — Claude proposed

- [☐] **Skills**: досвіду розробки замало для впевненої оцінки; навчання — частина мети проєкту.
- [☑] **Time**: 2–4 тижні вистачить за умови поетапності: етап 1 (ручне введення + каталог) ≈ 1 тиждень, етап 2 (імпорт) — далі.
- **State**: confirmed

## 13. Recommendation
**Selected: Approach C (у два етапи)** — етап 1: ручне введення ваги й часу, налаштування цін і каталог виробів, де ціна щоразу перераховується з поточних налаштувань; етап 2: імпорт файлу зі слайсера, а ручне введення лишається запасним шляхом. C закриває головну ринкову прогалину з §6: жоден інструмент не поєднує імпорт, каталог, гривню і мінімальний донат. У матриці §8 C — єдиний варіант з UX «+ найменше тертя загалом», тоді як A має «0 ручне введення, ризик помилок». RICE для C (16, §11) нижчий, ніж для чистого A (≈ 64), але A не досягає критерію швидкості без ручного переписування і не дає навчального досвіду інтеграції. Feasibility (§12: Tech ☑, Skills ☐, Time ☑ з поетапністю) прямо вимагає, щоб етап 1 сам по собі був робочим інструментом — тому C розбито на етапи.

**Locked-in pointer**: продукт — локальний настільний інструмент для одного користувача; каталог зберігає параметри виробу, а не готову ціну; ручне введення — обов'язковий запасний шлях; валюта — гривня; результат — мінімальний донат без націнки.
